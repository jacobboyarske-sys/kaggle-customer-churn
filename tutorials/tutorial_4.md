# Туториал 4. Feature Engineering

(~90-120 мин)

Цель — поднять ROC AUC выше baseline (0.8692 локально / 0.87486 на Kaggle) за счёт
работы с признаками, **не меняя модель** (та же `LogisticRegression` из туториала 3).
Это осознанное ограничение: если менять и признаки, и модель одновременно, вы не
поймёте, что именно дало эффект. Смена модели на градиентный бустинг — отдельный
туториал 5.

Код пишется в новом ноутбуке `notebooks/03_features.ipynb`. Стартуйте с копии кода
из `02_baseline.ipynb` (загрузка данных, `feature_cols`, split, Pipeline) — это
не копипаста ради лени, а осознанное решение сохранить неизменным всё, кроме
признаков, которые будете менять.

## Шаг 1. Исправить выброс в `EstimatedSalary`

В туториале 2 нашли 3 строки с аномальными значениями (15.75M, 6.09M, 1.48M) на
фоне нормального диапазона до ~200K. Клипирование по 99-му перцентилю:

```python
salary_cap = train["EstimatedSalary"].quantile(0.99)
train["EstimatedSalary"] = train["EstimatedSalary"].clip(upper=salary_cap)
test["EstimatedSalary"] = test["EstimatedSalary"].clip(upper=salary_cap)
```

**Важно:** `salary_cap` считается только по `train`, но применяется к обоим
датасетам. Если бы вы считали перцентиль по `train + test` вместе, информация из
test незаметно просочилась бы в предобработку — тот же принцип data leakage, что и
с `StandardScaler` в туториале 3.

Прогоните baseline-пайплайн заново с этим исправлением и сравните ROC AUC с
исходным 0.8692 — тремя выбросами из 15000 строк логрегрессия могла управлять с
не таким большим эффектом, как кажется на первый взгляд (`StandardScaler`
чувствителен к выбросам, но 3 строки — это 0.02% данных). Само по себе интересное
наблюдение, если эффект окажется маленьким.

## Шаг 2. Проверить нелинейность `NumOfProducts`

```python
train.groupby("NumOfProducts")["Exited"].agg(["mean", "count"])
```

В туториале 2 линейная корреляция была -0.29 (отрицательная), но линейная
корреляция не различает "чем больше, тем меньше" от "U-образная зависимость с
провалом посередине". Для реального банковского оттока обычно оказывается, что
2 продукта — самый лояльный сегмент, а 3-4 — наоборот, зона повышенного риска
(часто из-за того, что клиенты с 3-4 продуктами — это те, кому агрессивно
допродавали, и они уходят массово). Проверьте, подтверждается ли это здесь.

Если подтвердится — линейная модель (`LogisticRegression`) не сможет уловить
U-образную форму напрямую (она моделирует только монотонную зависимость от
числового признака). Решение — превратить `NumOfProducts` в категориальный
признак (`OneHotEncoder`, как `Geography`/`Gender`), а не оставлять числом:

```python
categorical_cols = ["Geography", "Gender", "NumOfProducts"]
```

## Шаг 3. Новые признаки

Три кандидата, независимо друг от друга — добавляйте по одному и проверяйте эффект
каждого:

```python
train["IsBalanceZero"] = (train["Balance"] == 0).astype(int)
test["IsBalanceZero"] = (test["Balance"] == 0).astype(int)
```

В туториале 2 распределение `Balance` было бимодальным (много нулей + отдельная
масса ненулевых значений) — отдельный флаг может нести больше сигнала, чем сырое
число, для линейной модели.

```python
train["AgeGroup"] = pd.cut(train["Age"], bins=[0, 30, 40, 50, 60, 100], labels=False)
test["AgeGroup"] = pd.cut(test["Age"], bins=[0, 30, 40, 50, 60, 100], labels=False)
```

`Age` — самый сильный числовой предиктор (корреляция 0.46 из туториала 2), но
линейная модель предполагает, что риск растёт строго пропорционально возрасту.
Биннинг проверяет гипотезу, что реальная зависимость ступенчатая (например, резкий
рост риска после 50), а не гладкая линия.

```python
train["BalanceSalaryRatio"] = train["Balance"] / (train["EstimatedSalary"] + 1)
test["BalanceSalaryRatio"] = test["Balance"] / (test["EstimatedSalary"] + 1)
```

`+ 1` в знаменателе — защита от деления на ноль, если вдруг встретится нулевая
зарплата (обычная практика для отношений признаков).

## Шаг 4. Target encoding для `Geography`

One-hot превращает `Geography` в 2 бинарные колонки (после `drop="first"`).
Target encoding — заменить категорию на средний `Exited` внутри неё (то самое
число из туториала 2: Германия 0.408, Франция 0.153, Испания 0.166), сохраняя
информацию о *силе* эффекта, а не только о наличии категории.

```python
geo_target_mean = X_train.join(y_train).groupby("Geography")["Exited"].mean()

X_train["Geography_te"] = X_train["Geography"].map(geo_target_mean)
X_val["Geography_te"] = X_val["Geography"].map(geo_target_mean)
test["Geography_te"] = test["Geography"].map(geo_target_mean)
```

**Критично:** `geo_target_mean` считается только по `X_train` (после сплита из
туториала 3), не по всему `train`. Если посчитать средние по всему `train`
(включая будущую `X_val`), каждая строка в `X_val` неявно "видела" саму себя через
среднее по своей группе — классическая утечка данных при target encoding, одна из
самых частых ошибок начинающих на Kaggle. Именно поэтому этот шаг идёт после
шага сплита, а не до него.

После этого `Geography` (исходную текстовую колонку) можно убрать из
`categorical_cols`, оставив только `Geography_te` как числовой признак.

## Шаг 5. Измерить эффект каждого шага изолированно

После **каждого** пункта (1-4) прогоняйте одну и ту же связку
`ColumnTransformer + LogisticRegression` и записывайте ROC AUC на валидации в
табличку (прямо в ноутбуке, markdown-ячейкой):

```
baseline (туториал 3):        0.8692
+ клип EstimatedSalary:       0.XXXX
+ NumOfProducts как категория: 0.XXXX
+ IsBalanceZero:              0.XXXX
+ AgeGroup:                   0.XXXX
+ BalanceSalaryRatio:         0.XXXX
+ Geography target encoding:  0.XXXX
```

Если какой-то шаг **ухудшил** ROC AUC — это не ошибка процесса, а полезный
результат: значит, эта гипотеза не подтвердилась на этих данных, и признак можно
убрать. Так делает большинство сильных Kaggle-решений — итеративно, с измерением,
а не "накидать побольше фичей и надеяться".

- Не просите сразу "сделай feature engineering" — по одному признаку за раз, с
  измерением, это и есть весь смысл туториала.
