# Туториал 2. EDA — разведочный анализ данных

(~60-90 мин)

Цель этого этапа — не построить модель, а понять данные настолько, чтобы
осознанно принимать решения на следующих этапах: как кодировать признаки, какую
стратегию валидации выбрать, чему вообще можно верить в данных. Весь код пишется в
`notebooks/01_eda.ipynb` (том же, где в туториале 1 был sanity-check).

Сначала — новые зависимости для графиков:

```powershell
pip install -r requirements.txt
```

## Шаг 1. Общая структура данных

Загрузите `train.csv` и `test.csv` (если ноутбук уже открывали в туториале 1 — это
уже сделано, просто перезапустите ячейку). Дальше — база: сколько строк/столбцов,
какие типы данных, есть ли дубликаты.

Вопросы, на которые должен ответить этот шаг:
- `train.shape`, `test.shape` — сколько строк и признаков.
- `train.dtypes` / `train.info()` — какие колонки числовые, какие текстовые/категориальные.
- Есть ли дубликаты по `CustomerId` (`train["CustomerId"].duplicated().sum()`) —
  если банковский клиент не должен повторяться дважды, дубликат может быть сигналом
  проблемы в данных.

## Шаг 2. Пропущенные значения

```python
train.isnull().sum()
test.isnull().sum()
```

Для синтетического датасета пропусков, скорее всего, не будет — но проверять эту
привычку стоит закрепить на любом датасете, реальном или нет: код, который молча
предполагает "пропусков нет", ломается на следующем датасете, где они есть.

## Шаг 3. Баланс классов `Exited`

```python
train["Exited"].value_counts(normalize=True)
```

Это один из самых важных чисел во всём проекте. Если, например, только ~20%
клиентов ушли (`Exited=1`), это означает:
- Accuracy как метрика была бы бесполезна (модель, всегда предсказывающая "0",
  получила бы ~80% accuracy, ничего не предсказывая) — хорошо, что организаторы
  выбрали ROC AUC, она устойчива к дисбалансу.
- В туториале 5 кросс-валидация обязана быть **стратифицированной**
  (`StratifiedKFold`, а не просто `KFold`) — иначе некоторые фолды могут получить
  непропорционально мало примеров `Exited=1`, и локальный CV score будет шумным и
  не будет соответствовать реальному качеству модели.

Постройте также barplot (`sns.countplot`) — просто чтобы увидеть дисбаланс
визуально, не только в цифрах.

## Шаг 4. Числовые признаки

Колонки: `CreditScore`, `Age`, `Balance`, `EstimatedSalary`, `Tenure`,
`NumOfProducts`. Для каждой — гистограмма (`sns.histplot` или `train[col].hist()`).

На что смотреть:
- Форма распределения (нормальное, скошенное, бимодальное) — это подскажет, нужны
  ли трансформации (например, лог-трансформация для скошенных распределений вроде
  `Balance`, где часто много нулей плюс длинный хвост).
- Выбросы — значения, сильно оторванные от основной массы (`Age` под 100 лет,
  отрицательный `Balance` и т.п. — стоило бы насторожиться, хотя для синтетики
  таких сюрпризов обычно меньше, чем в реальных данных).
- `NumOfProducts` и `Tenure` по сути дискретные (мало уникальных значений) — для
  них удобнее не гистограмма, а `value_counts()` или countplot.

## Шаг 5. Категориальные признаки и churn rate по группам

Колонки: `Geography`, `Gender`, `HasCrCard`, `IsActiveMember`. Для каждой — два
взгляда:

```python
train["Geography"].value_counts()
train.groupby("Geography")["Exited"].mean()
```

Первая строка — просто сколько клиентов в каждой категории (баланс представленности).
Вторая — самое важное: средний `Exited` внутри каждой группы — это **churn rate**, и
если он заметно различается между категориями (например, отток в одной стране вдвое
выше, чем в других), это прямой сигнал, что признак полезен для модели, ещё до
всякого feature engineering.

Проделайте то же для `Gender`, `HasCrCard`, `IsActiveMember`. Гипотеза, которую
стоит держать в голове: `IsActiveMember` — по смыслу признака ожидаемо, что
неактивные клиенты уходят чаще; если данные это подтверждают, это сильный сигнал.

## Шаг 6. Корреляции

```python
train[numeric_cols + ["Exited"]].corr()
```

Два разных вопроса в одной матрице:
- **Корреляция признаков с `Exited`** — грубая, но быстрая оценка, какие числовые
  признаки вообще связаны с оттоком (учтите: линейная корреляция не ловит
  нелинейные и пороговые зависимости, поэтому это ориентир, а не приговор).
- **Корреляция признаков друг с другом** (мультиколлинеарность) — если два признака
  почти дублируют друг друга, для линейных моделей (baseline в туториале 3) это
  может быть проблемой, для градиентного бустинга (туториал 5) — как правило нет.

Визуализация: `sns.heatmap(corr, annot=True, cmap="coolwarm")`.

## Шаг 7. train vs test — совпадают ли распределения

Данные синтетические — сгенерированы моделью, обученной на реальном датасете, а
значит стоит проверить, что `train` и `test` не "разъехались" (иначе локальная
валидация будет обманчиво хорошей или плохой относительно реального лидерборда).
Для 2-3 ключевых числовых признаков наложите гистограммы train и test на одном
графике (`sns.histplot` с `hue` или два вызова `plt.hist` с `alpha=0.5`).

Если распределения визуально совпадают — хороший знак, можно спокойно доверять
локальной валидации как прокси для реального score.

## Шаг 8. Выводы

В последней ячейке ноутбука — markdown-ячейка с 2-3 короткими выводами: какие
признаки выглядят многообещающими, есть ли дисбаланс классов и как с ним быть,
есть ли что-то подозрительное в данных. Эти выводы — отправная точка для
feature engineering в туториале 4, не нужно решать всё прямо сейчас, важно просто
зафиксировать гипотезы, пока они свежие.

## Как использовать Claude Code на этом этапе

- Пишите код по одной ячейке за раз и просите ревью: *"Я хочу посчитать churn rate
  по Geography — вот мой код, я что-то упускаю?"*
- Если непонятен график или число — спрашивайте "почему это так", а не просто
  "как построить график". Например: *"Почему для NumOfProducts лучше countplot, а
  не histplot?"*
- Не просите Claude Code сразу "сделай весь EDA" — это ровно тот случай, когда
  сам процесс смотрения на данные важнее готового результата.

## Проверка (пройдите по порядку)

1. Известны `shape` train и test, и понятно, какая колонка отсутствует в test
   (`Exited`).
2. Известен процент пропусков (даже если он 0%).
3. Известен баланс классов `Exited` — конкретное число, не "примерно поровну".
4. Есть гистограммы всех числовых признаков.
5. Посчитан churn rate по каждой категориальной колонке.
6. Построена матрица корреляций с визуализацией.
7. Проверено (хотя бы для нескольких признаков), что train и test распределены похоже.
8. В ноутбуке есть текстовый вывод с гипотезами для feature engineering.
