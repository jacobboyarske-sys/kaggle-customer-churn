# Kaggle: Predicting Customer Churn — учебный проект

Решение соревнования Kaggle
["Predicting Customer Churn: Binary Classification"](https://www.kaggle.com/competitions/predicting-customer-churn-a-real-world-binary-classification-challeng):
предсказать вероятность оттока клиента банка (`Exited`, 0/1) по его демографическим
и account-признакам. Метрика — ROC AUC.

**Главная цель проекта — не сам score, а то, что вы пройдёте весь ML-пайплайн
самостоятельно**, используя Claude Code как ассистента-ревьюера, а не автора.
Amбициозная, но осмысленная планка: попасть в топ-10 финального лидерборда
(ROC AUC ≈ 0.933+ — подробнее в [CLAUDE.md](../CLAUDE.md)).

Каждый этап оформлен отдельным файлом `tutorial_N.md` в этой папке — по мере
прохождения появляется следующий номер.

## Как работать с Claude Code в этом проекте

Те же привычки, что и в проекте KidsMap Moscow:

1. **Маленькие задачи.** Не просите "сделай весь пайплайн" — просите "напиши
   функцию, которая кодирует Geography one-hot'ом" или "посчитай ROC AUC на
   валидации для baseline-модели".
2. **Обсуждение перед крупными шагами.** Перед новым этапом (например, "перейти на
   градиентный бустинг") сначала обсудите план с Claude Code, потом переходите к коду.
3. **Всегда читайте diff/код перед принятием.** Особенно важно для ML — код может
   быть рабочим, но со скрытой утечкой данных (data leakage) в валидации.
4. **CLAUDE.md — память проекта.** Обновляйте его, когда меняются договорённости
   (например, выбрали финальную модель или изменили стратегию валидации).
5. **Коммитьте после каждого этапа**, просматривая `git status`/`git diff` сами.
6. **Спрашивайте "почему".** Если Claude Code предлагает модель/метрику/способ
   кодирования признаков — просите объяснить альтернативы. Это и есть тренировка
   ML-интуиции, а не просто рабочий сабмит.

| tutorial_8.md | Финализация: сравнение экспериментов, финальный сабмит | впереди |

Краткое содержание этапов:

- **Окружение** — venv, `requirements.txt`, настройка Kaggle API (токен), скачивание
  `train.csv`/`test.csv`/`sample_submission.csv`, первый коммит.
- **EDA** — распределения признаков, пропуски, баланс классов `Exited`, корреляции,
  первые гипотезы о полезных фичах.
- **Baseline** — логистическая регрессия или простое дерево, локальная валидация
  (train/val split), первый сабмит на Kaggle — чтобы пайплайн end-to-end заработал
  как можно раньше и было с чем сравнивать дальнейшие улучшения.
- **Feature engineering** — кодирование категориальных признаков (`Geography`,
  `Gender`), скейлинг, новые признаки (например, комбинации `Balance`/`NumOfProducts`).
- **Градиентный бустинг** — LightGBM/CatBoost, корректная K-Fold кросс-валидация со
  стратификацией по таргету (важно из-за дисбаланса классов).
- **Тюнинг и ансамбли** — подбор гиперпараметров, blending нескольких моделей —
  ровно то, что нужно, чтобы пройти путь от "средней" модели (~0.86-0.90 ROC AUC) до
  топ-10 группы (~0.93+).
- **Интерпретируемость** — feature importance, SHAP-графики: какие признаки реально
  двигают предсказание и почему (соревнование явно просит подумать об этом).
- **Финализация** — сравнение всех экспериментов, выбор и объяснение финальной
  модели, README проекта.

## Примерный тайм-лайн

При 1-2 сессиях в неделю по 2-4 часа весь путь (туториалы 1-8) — это 4-6 недель.
Соревнование уже завершено (Late Submission), так что спешить с дедлайном не нужно —
можно спокойно пройти каждый этап вдумчиво.

## Что можно скорректировать по ходу

- Если топ-10 окажется недостижим без экзотики (например, потребует stacking из
  10 моделей) — это тоже полезный вывод, обсудим и скорректируем цель на "топ-15"
  или "переиграть собственный baseline на X%".
- Порядок этапов 6 (тюнинг/ансамбли) и 7 (интерпретируемость) можно поменять
  местами — если интереснее сначала понять, что вообще влияет на предсказание, а
  потом уже жать score.
